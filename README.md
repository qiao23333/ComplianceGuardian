## 为什么做这个

在移民行业做内容运营时，我遇到的真实情况是：

通用合规工具（句易网、零克查词等）只检测广告法极限词，而移民/留学内容的合规红线
**几乎全在通用词库之外**：

| 违规表述 | 性质 | 通用工具 |
|---|---|---|
| 保证下签 / 包过 / 成功率100% | 虚假承诺（《广告法》第28条） | ❌ 不覆盖 |
| 内部关系 / 移民局有人 / 内部名额 | 违法操作暗示 | ❌ 不覆盖 |
| 现成雇主 / 挂靠雇主 / 包安排雇主 | 雇主担保红线 | ❌ 不覆盖 |
| 3个月必拿PR / 保证X天获批 | 时间承诺 | ❌ 不覆盖 |
| 全网最低价 / 不成功全额退款 | 费用承诺 | 部分覆盖 |

再加上小红书 / 抖音 / 视频号三套平台规则、蓝V企业号与个人号的不同标准，
每发一条内容都要人工反复核对四个维度，效率极低。

所以我做的不是"又一个违禁词检测器"，而是**面向垂直行业的合规助手** ——
把"行业红线 + 平台差异 + 账号类型"这三层判断做成一次检测。

## 可量化的效果

工具的可信度不取决于"规则条数"，而取决于**误报率**与**漏检率**。
项目内建了一份评测语料（`tests/corpus/`），把这两个数字变成可回归的指标：

| 指标 | 改造前 | 当前 | 含义 |
|---|---|---|---|
| 误报率（合规文案被误判） | **35.5%** | **0%** | 误报高 → 运营直接弃用工具 |
| 漏检率（违规文案连提示都没有） | **26.7%** | **0%** | 漏检高 → 工具没有价值 |
| 仅提示率（只判警告未判违规） | — | 10% | 红线表述不该只落在"提示"级 |

误报率的下降来自一次设计思路的切换，详见下文「设计决策」。

测试规模：**290 个 pytest 用例** + **108 项浏览器冒烟** + **WCAG 对比度审计**，
含反误报/反漏检语料门禁、UI 布局约定守卫、双端引擎对拍、断网可用性验证。

## 核心能力

### 1. 三平台 × 双账号矩阵检测

同一段文案，一次给出小红书 / 抖音 / 视频号三个平台的独立判定，
并**归因差异来源**：

- 三平台分数并列时，明说"判定一致，命中的是跨平台通用规则"，不制造不存在的结论；
- 存在差异时，指出"哪个平台有独有的风险词"以及"分数差多少"。

### 2. 行业词库包（可插拔）

新增一个行业不需要改内核代码，只需在 `rules/industry_packs/` 下加一个目录：

```
rules/industry_packs/immigration/
├── pack.json    # 包元数据：id / 名称 / 版本 / 分类说明
└── rules.json   # [ {keyword, category, severity, suggestion, note}, ... ]
```

内置 9 个包共 475 条：

| 行业包 | 条数 | 主要依据 |
|---|--:|---|
| 移民 / 出境入境 | 171 | 《国务院关于出境入境管理的规定》（国务院令第 841 号，2026-09-15 施行）第十条六条禁令 |
| 医疗美容 | 52 | 《广告法》第十六条、第十七条；《医疗机构管理条例》 |
| 教育培训 | 42 | 《广告法》第二十四条 |
| 食品保健 | 39 | 《食品安全法》第七十三条；《广告法》第十七条、第十八条 |
| 房地产 | 37 | 《广告法》第二十六条；《房地产广告发布规定》第十八条 |
| 电商带货 | 36 | 《广告法》第二十八条；《电子商务法》第十七条 |
| 金融理财 | 35 | 《广告法》第二十五条；《证券法》 |
| 美妆护肤 | 33 | 《化妆品监督管理条例》第二十二条、第四十三条 |
| 留学 / 升学 | 30 | 《广告法》第二十四条第一项；《国务院关于出境入境管理的规定》第十条第一项 |

行业包一律要求写 `law_ref`（100% 覆盖），且不得与旧库或其他包撞关键词 ——
同一处命中挂两个来源，用户说不清按哪条算分。这两条都由
`tests/test_industry_packs.py` 守着。

### 3. 反误杀：语境守卫（这是最难的部分）

中文里"第一"既可能是绝对化宣传（"行业第一"），也可能是普通序数
（"第一步 / 第二阶段 / 第3步"）。纯词表匹配会把后者全部误报 ——
而这类句式在移民/留学文案里出现频率极高。

合规卫士用两层判定：**规则层负责命中，语境层负责否决**。

- `EXEMPT_PHRASES`（短语表）：处理固定搭配（最近 / 最后 / 最终 / 顶级域名…）
- `EXEMPT_PATTERNS`（语法模式）：处理可穷举骨架的句式
  （`第X + {步|阶段|章|篇|次|位…}`、`首个 + {工作日|季度|阶段…}`）

判定规则：命中区间**被豁免区间完全覆盖**时才算豁免。
所以"销量第一""位列行业第1位"依旧全部报出，而"我排在第1位""第2步递交EOI"
不再误报 —— 放宽与收紧是成对设计的，不是单边放宽。

### 4. 建议改写闭环

每条风险都带 `suggestion`（如"保证下签"→"改为'协助递交申请'"），
并支持一键生成"修改后文案"。短词（长度 1 的极限词）被禁止自动改写 ——
否则"最近很多人问我"会被改成"近很多人问我"，属事故级错误。

### 5. 词库管理与批量检测

可视化增删改自定义规则、词库版本备份与恢复、跨词库去重冲突检测；
批量扫描文件夹输出风险分布汇总，可导出 CSV / Excel。

### 6. 本地优先，AI 零配置可用

纯本地运行，文案不出本机。AI 改写可以走本地 Ollama（可选，隐私最好）。

但更关键的是**不配任何模型也能用上 AI**：点「复制改写指令」，工具会把规则引擎的
精确命中（含法条来源与可用替换词）连同改写约束打包成一段文本，粘到任意 AI 里即可
拿到改写结果。零注册、零 API Key、零成本，文案也不经过任何服务器（本工具确实没有
服务器）。Web 体验页因此可以纯静态部署。

### 7. AI 只做改写，不做判定

这是本项目对"AI 该用在哪"的明确回答，也是和市面上"把文案丢给大模型让它判违规"
那类做法的根本区别：

- **判定**（违不违规、几级、扣几分）→ **规则引擎**。判定要确定、可复现、可追溯，
  模型会漏检、会凭空发明违规、同一句话问两次给两个答案。
- **改写**（把违规的说法换成合规又保住卖点的说法）→ **语言模型**。这是语言活儿，
  规则库给不出"保签包过"该改成什么才既有说服力又不承诺结果。

提示词里把这条边界写死了（"不要做合规判定"，并说明原因）。
完整论述见 **[docs/AI-USAGE.md](docs/AI-USAGE.md)**。

### 8. 改稿闭环，而不只是打分

内容运营的真实节奏是**检测 → 改 → 再检测 → 再改**，所以光有一把尺子不够。

Web 端可以「存为改前」建立基线，之后每改一次就实时给出：

- 改前分 → 改后分、已消除 N 处、仍未处理 M 处
- **新引入 K 处** —— 这块存在的理由。改文案时改出新违规是常态，
  而多数工具只告诉你"还剩几处"，不告诉你"你刚才那一刀又砍出个新问题"。

基线只存在内存里，刷新即失效，不落盘、不留原文。

Web 端还是一个 **PWA**：可以装到桌面 / 手机主屏，第一次打开之后**断网也能用**。
缓存策略是 HTML 走 network-first、静态资源走 stale-while-revalidate，
所以既不会看到旧版本，也不需要把版本号手写进缓存名。冒烟测试里真的开了
`setOfflineMode(true)` 再刷新，验证的是"拔了网线照样跑"，而不是"注册成功"。

### 9. 依据可追溯到条款号，而不只是"来源=广告法"

说某句违规，得说得出**违反哪一条**。否则它只是违禁词表：用户没法复核、
没法拿去跟平台申诉、没法给法务看。

命中卡片、报告、批量 CSV、词库页都会带出 `《广告法》第九条` 这样的条款号
与规则说明（"无激素类表述需检测报告支撑"这类**什么条件下才合规**的信息）。

- 覆盖率是**可量的**：法条类词库 610 / 710 条标注了条款依据（约 86%），
  词库页一眼可见；平台规则与蓝V规则不标法条，因为它们的依据是平台规范。
- 补条款号走幂等脚本 `scripts/enrich_law_refs.py`，映射表与**判定理由**
  一起写在代码里——宁可显示"该来源暂无条款依据"，也不猜一条错法条。
- 未标依据的类别（雇主担保红线 / 违法操作 / 关系暗示）在脚本里写明理由：
  它们指向买卖 offer、挂靠、走后门，性质是经营许可与欺诈，**不属于广告法
  调整范围**，硬挂一条广告法反而是错的。

### 10. 规则会安静地过期，所以做了会失败的门禁

这是这类工具**最大的真实风险**，也是最容易被忽略的：

> 检测准确率再高，也只对"词库写下那天"的规则成立。平台规则几个月一改，
> 监管口径随政策走。功能不报错、测试不变红、页面照常给分数——
> 只是分数开始失真。规则驱动型工具不是死于做不出来，是死于没人维护。

- `rules/review_log.json` 记录每个来源的**依据 / 上次复核日 / 复核周期 /
  复核要点**；Web 词库页顶部的「词库健康度」把它做成可扫一眼的指标。
- `scripts/check_rule_freshness.py` 超期即返回退出码 1，已进 CI。
  它同时会指出"词库里有、台账里没登记"的来源——忘了登记就永远不会被提醒。
- 台账里只存**事实**（复核日、周期），"还剩几天"由浏览器现算。
  把剩余天数写进产物，产物就会每天漂移，双端对拍门禁会天天变红。

### 11. 用户自己的词库：工具没收录的，你自己补

通用工具的宿命是"永远缺一个词"—— 每家公司都有自己的内部禁用表达
（竞品名、老板不爱听的说法、以前被平台警告过的词）。

- Web 端「我的词库」页：单条 / 批量添加，可写风险等级、改写建议、依据备注。
  加完**立刻参与检测**，命中时来源标成「我的词库」。
- 数据只存在浏览器 `localStorage`，不联网、不上传 —— 和页面"文案不出本机"的
  承诺一致。换设备靠导出 / 导入 JSON。
- 导出是**裸数组 JSON**，与桌面端 `rules/user_custom.json` 同一格式。
  互导的前提是格式真的只有一种：包一层 `{meta, rules}` 就再也读不回来。
- 与内置词条同名的会被挡下并说明理由 —— 理由见「已知边界」最后一条。
- 停用开关是真的从引擎里摘掉，不是只把那一行变灰（冒烟测试真跑一遍检测来验）。

### 12. 移动端：不是"缩小"，是重新排

手机上原来的毛病是功能性的，不是视觉的：标签在文档流顶部，滚到中间想切页得先
滚回去；平台 / 账号 / 行业几个控件摊开占掉整屏，想看检测结果得先把设置折起来。

- 标签栏在 ≤720px 下变成**固定在底部**的 4 格导航。复用同一份 DOM，靠 CSS 换位 ——
  复制一份 DOM 迟早两份不同步。
- 检测设置在窄屏自动折成一行摘要，摘要里直接写出当前配置（"三平台 · 普通号 · 移民"），
  不用展开也知道自己在测什么。
- 词库筛选同样收成折叠块，并带"已启用 N 项"角标。
- 输入类控件一律 16px：iOS 对 `font-size < 16px` 的输入框会自动放大整页，
  这是"难用"最直接的来源。这里踩过一个坑 —— 基础样式写的是 `textarea#input`
  （特异性 1,0,1），窄屏只写元素选择器 `textarea`（0,0,1）压不过它，
  字号"看着改了其实没改"，而且不报错。
- 这些都不靠肉眼验收：`web_smoke.mjs` 在 390px 视口下逐项量几何
  （标签栏是否真在底部、控件是否 ≥42px、有没有横向溢出、切页后滚动是否归零）。

## 架构

```
┌──────────────────────────────────────────────────────────┐
│                      呈现层（双端同源）                    │
│   apps/desktop/  桌面端（CustomTkinter，6 个页面）         │
│   web/           浏览器端（零安装体验页，含 JS 引擎）       │
└───────────────────────────┬──────────────────────────────┘
                            │  同一份判定语义
┌───────────────────────────▼──────────────────────────────┐
│                    guardian/  内核（纯逻辑）               │
│                                                          │
│  rulebank.py     规则银行：加载 / 变体展开 / 优先级仲裁     │
│  matcher/        Aho-Corasick 自动机（可降级纯 Python）     │
│  normalize/      繁简转换 / 拼音变体 / 空格干扰还原         │
│  context_guard.py 反误杀守卫：短语表 + 语法模式            │
│  engine.py       检测主流程：多源命中 → 去重 → 定级 → 评分   │
│  detector.py     对外门面（单例）+ 跨平台批量               │
│  batch_detect.py 批量扫描 / 汇总 / CSV·Excel 导出           │
│  export_report.py HTML / PNG / PDF 报告                     │
│  storage.py      SQLite 历史库（原子写入）                  │
│  llm/            AI 改写能力（只管改写，不参与判定）        │
└──────────────────────────────────────────────────────────┘
```

**内核纪律**：`guardian/` 只允许依赖标准库与纯 Python 包，
禁止 import tkinter / fastapi —— 保证桌面端、Web 端、脚本三处能共用同一套判定。

## 关键设计决策

| 决策 | 为什么这样做 | 放弃了什么 |
|---|---|---|
| 语境守卫用「短语表 + 语法模式」双层，而不是纯词表 | 用有限枚举对抗无限语言变体是打地鼠；"第X步/第X阶段"这类是**可穷举骨架**的句式 | 语法模式需要人工归纳量词表，覆盖不到的量词仍需补短语 |
| 豁免判定要求"命中区间被豁免区间**完全覆盖**" | 防止"销量第一"因为句中出现"第一"而被整体放过 | 部分边界表述（如"第3名"）无法豁免，宁可多提示 |
| 放宽一条的同时补一条精确规则 | 例：豁免"第X位"（位次语义）＋ 新增 `(位列\|排名\|位居)第X位` 正则 | 规则文件更长，但误报与漏检不会此消彼长 |
| 单字极限词降级为 `low` 且禁止自动改写 | 单字误杀面极大，且自动改写会破坏原文 | 单字风险不再计入分数，只做提示 |
| 内核与 UI 严格分层，双端对拍验证 | 跨端判定漂移是这类工具最隐蔽的 bug | 需要维护导出脚本与对拍脚本 |
| 四级严重度而非"违规/警告"二分 | 二分法把"封号级"和"建议修改"混在一档，用户无法排优先级 | 需要给每条规则定级，词库治理成本上升 |
| **判定归规则引擎，只把改写交给 AI** | 判定要确定、可复现、每条都可追溯到法条；模型做判定会漏检、会幻造违规、同问两答。改写是语言活儿，才是模型的主场 | AI 效果取决于用户自己配的模型；不配模型时走 BYO-AI 复制指令，多一步粘贴 |
| 提示词里写明"不要做合规判定"并给出原因 | 只写"要什么"不够，模型会顺手多做判定，引入不稳定 | 提示词变长，且需要测试守住（`tests/test_rewrite.py`） |
| AI 不可用时不算失败，而是给替代路径 | "没有 AI 也是完整产品"是底线，不该让用户卡在报错弹窗 | 失败分支多一个交互 |
| 词库改动写成幂等脚本（`scripts/harden_rulebank.py`） | 手改 JSON 无法追溯，也无法复现；脚本每条改动写明理由 | 需要额外维护脚本与预览/校验流程 |

## 已知边界（诚实说明）

- **文本检测，不理解语义**：靠词表 + 正则 + 语境模式，无法判断"反讽""引用""辟谣"等语境。
  这是**刻意的取舍**：判定必须可复现、可追溯，所以不把模型的不确定性引进来。
- **AI 只做改写，不改判定**：AI 的产出要用户复核，UI 上逐处标明"改前 → 改后"；
  模型明确说改不了的（`unresolved`）会如实呈现，不硬凑方案。
- **Web 端不含拼音变体通道**：拼音库体积大且误报率高，只保留繁简 / 全角 / 谐音 / 跳字。
  拼音规避写法请用桌面端。
- **行业包只覆盖 9 个行业**：这是目前能核实到依据的范围。再加行业需要真的
  查清该行业的监管条文再写，宁可少也不要塞一堆没依据的词。
  用户自己行业的词可以走「我的词库」自定义补充（本地存储，可导出互导）。
- **自定义词条不能覆盖内置判定**：与内置词条同名的词会被挡下并提示"已收录"。
  允许重名会让同一处命中挂两个来源，页面上同一个词被判两遍，用户只会以为是 bug。
  真实需求（想调整内置词的定级）属于"覆盖定级"，是另一个功能，没有混进这个入口。
- **平台规则是经验归纳**：各平台规则会更新，词库需要人工维护跟进。
  已用 `review_log.json` 台账 + CI 门禁把"该复核了"变成会红灯的硬约束，
  但**复核本身仍然是人做的**——门禁只能提醒，不能替你读新规。
- **法条类词库约 86% 标到条款号**：剩下 14% 集中在雇主担保红线、违法操作、
  关系暗示等类别，它们不被广告法调整，所以刻意留空（见 `enrich_law_refs.py`）。
- **正则兜底会误伤边界表述**：例如"第3名"会被报出（排名语义），
  已通过语境守卫收敛，但不可能 100%。
- **严重度分级人工判定**：有明确法条依据的表述已校准，其余仍带主观性。
