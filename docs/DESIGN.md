# 设计决策与权衡

这份文档记录**为什么这样做**，以及为此放弃了什么。

功能列表在 README 里；这里只写判断过程 —— 尤其是那些"看起来可以更简单、
但简单做法会在真实使用中失效"的地方。

---

## 0. 先定义什么叫"好"

做内容合规工具，最容易陷入的自我欺骗是**用规则条数衡量成果**：
词库从 500 条涨到 1000 条，看起来很努力，但用户的实际体验可能变得更糟 ——
因为新增的规则多半会带来新的误报。

所以我先把"好"定义成两个互相拉扯的数字：

| 指标 | 定义 | 变坏之后会怎样 |
|---|---|---|
| **误报率** | 合规文案被判定为违规的比例 | 运营发现"正常文案也报错"，直接弃用工具 |
| **漏检率** | 违规文案连提示都没有的比例 | 工具给不了安全感，用户仍要人工复核，等于没用 |

这两个指标必然此消彼长：多收词降漏检但升误报，放宽语境降误报但升漏检。
**任何单边优化都是作弊**。所以项目里建了评测语料（`tests/corpus/`），
31 条合规文案 + 30 条违规文案，任何改动都必须同时报出这两个数字。

真实的历史数据（可复现，`python -c "from tests.corpus import report; print(report())"`）：

```
改造前：  误报率 35.5%   漏检率 26.7%
改造后：  误报率  0.0%   漏检率  0.0%
```

## 1. 语境守卫：从「枚举短语」升级为「语法模式」

### 问题

中文的"第一"承担两种完全不同的语义：

- **绝对化宣传**：行业第一、销量第一、全国第一 → 《广告法》第九条明令禁止
- **普通序数**：第一步、第二阶段、第3步、第一篇 → 完全正常的表述

纯词表匹配无法区分，于是后者被大量误报。而"第一步 / 第二阶段 / 第3步"
恰恰是移民、留学类文案里**出现频率最高**的句式（讲流程、讲材料清单、
讲时间线都离不开它）。

实测：31 条合规文案里 11 条被误报，**误报率 35.5%**，且全部是序数表达。

### 第一版做法（错的）

在豁免短语表里一条条加：

```python
EXEMPT_PHRASES = {
    "第一": ("第一次", "第一反应", "第一步", "第一天", "第一年", ...),
}
```

问题很清楚：这是**用有限枚举对抗无限的语言变体**。加了"第一步"，
"第二步"照样报；加了"第一天"，"第一个月"照样报；还有"第1步 / 第3步"
（阿拉伯数字）、"第一阶段 / 第X环节"…… 永远补不完。

### 最终做法

把豁免拆成两层，**短语表处理固定搭配，语法模式处理可穷举骨架的句式**：

```python
EXEMPT_PATTERNS = (
    # 第X步 / 第二阶段 / 第3点 / 第一篇 / 第2次 / 第1位
    re.compile(r"第[一二三四五六七八九十百零〇\d]+(?:个)?"
               r"(?:步|阶段|章|节|篇|条|次|天|年|月|周|期|轮|批|版|"
               r"层面|环节|时间|分钟|小时|季度|课|题|项|点|类|组|份|部分|位)"),
    # 首个工作日 / 首个季度
    re.compile(r"首(?:个|次)(?:工作日|自然月|月|季度|阶段|环节|版本|批次|申请季)"),
)
```

一次覆盖整类变体，而不是逐个补词。

### 关键约束：豁免必须"完全覆盖"

判定条件是**命中区间被豁免区间完全覆盖**才豁免：

```
"销量第3名"
  ↑ 违规正则命中 "第3"  [0,3)
  但豁免模式匹配的是 "第3名"？—— 不，量词表里刻意没有 "名"
  → 不豁免 → 正确报出 ✅

"第一步先准备材料"
  违规命中 "第一" [0,2)
  豁免区间 "第一步" [0,3) 完全覆盖 [0,2) → 豁免 ✅
```

这条约束是"放宽"的安全阀：**放宽一条语境规则时，只有落在该句式内部
的命中会被放走，孤立的绝对化表述照报**。

### 量词表为什么这么短

量词表只收"流程、阶段、章节、次数、时间、编号"这几类**纯结构性量词**。
刻意**不收**的名词：

- `第一品牌 / 第一选择 / 第一方案` —— 这些**可能**是排名宣传，宁可漏豁免不可漏检
- `第X名` —— 广告语境里"第3名"基本就是排名宣称（"销量第3名"），所以**不豁免**

`第X位` 是唯一一个微妙的情况，见下条。

## 2. `第X位` vs `第X名`：一个量词引发的思考

`我排在第1位等待补料通知` —— 这是**位次**，不是宣传，应该豁免。
`我们位列行业第1位` —— 这是**排名宣称**，应该报出。

如果只做"豁免第X位"，第二句就漏了；如果只做"报出第X位"，第一句就误报。

**结论：放宽与收紧必须成对设计，不能单边放宽。**

```
语境守卫层：  豁免 "第X位"（因为位次语义占多数）
规则层：      新增正则 (位列|排名|位居|荣登|蝉联)(行业|全国|…)第X位
```

两句各自的判定结果：

| 文案 | 豁免区间 | 结果 |
|---|---|---|
| 我排在第1位等待补料 | `第1位` 覆盖命中 | ✅ 不报（位次） |
| 我们位列行业第1位 | `第1位` 覆盖"第X位"命中，但 `位列行业第1位` 被新增正则整段命中 | ✅ 报出（排名宣称） |
| 排名第1位的中介 | 同上 | ✅ 报出 |

这个"成对"原则在此后所有语境调整里都沿用。

## 3. 死规则：规则条数是虚荣指标

用词库质量脚本扫描时发现 6 条这样的规则：

```json
{"keyword": "保证X天获批", "category": "时间承诺", "severity": "warning"}
{"keyword": "我家XX", "category": "虚假种草"}
```

`X` 是占位符，**永远不会匹配任何真实文本**。这类规则只做一件事：
把"规则总数"的数字撑大。

而讽刺的是，`保证3个月出签` —— 移民行业最高频的违规表述之一 ——
词库里有它的"影子"（`保证X天获批`），却抓不到它本身。

处理方式：写 `scripts/harden_rulebank.py`，把占位符规则改写成**等价正则**，
让它真能命中：

```json
{"keyword": "保证\\s*[\\d一二三四五六七八九十两]+\\s*(?:天|周|个?月|年)\\s*(?:内)?\\s*(?:获批|下签|出签|拿到)",
 "match_mode": "regex",
 "severity": "high"}
```

同时把严重度从"提示"提到"高危"—— 在移民语境下承诺获批时间属于虚假承诺
（《广告法》第28条），不是"建议修改"级。

**顺带补上**实测缺失的高频违规表达：`现成雇主 / 现成岗位 / 现成担保`（雇主担保红线）、
`最后一波 / 名额有限 / 错过再等一年 / 仅剩N个名额`（稀缺营销）。

脚本的三个设计约束：幂等（反复跑不会重复插入）、可 `--dry-run` 预览、
每条改动写明理由。**手改 JSON 无法追溯、无法复现，所以词库治理必须脚本化。**

## 4. 严重度的分档是功能，不是装饰

旧体系只有 `violation / warning` 两档，映射到四级后出现：

```
critical 654 / medium 379 / high 0    ← 四级里有一档永远是空的
```

结果就是：**所有违规都被喊成"封号级"**，用户看完一屏红色之后，
无法判断哪一条必须先改。等于没有分优先级。

重分级后按法律与平台后果分档：

| 档位 | 判据 | 示例 |
|---|---|---|
| `critical` | 违法 / 封号级 | 挂靠雇主、买身份、入籍承诺、医疗功效 |
| `high` | 明确违规 / 限流级 | 极限词、虚假承诺、导流违规、时间承诺 |
| `medium` | 建议修改 | 绝对化用语、引诱消费、比较广告 |
| `low` | 仅提示 | 单字极限词（误杀面太大，不计入分数） |

配套的一次校准：`全网最低 / 全国最低 / 史上最低 / 百分百` 由 `medium` 提到 `high`。
理由：《广告法》第九条 + 《价格法》第十四条明确禁止虚假的最低价格宣称，
与极限词同级法律风险，留在"低危建议"档会被用户直接划过。

注：这次改动让一个既有测试失败（它正用"全网最低"当 medium 档的代表词）。
**改测试而不是改回代码** —— 因为提级有明确法条依据，测试的期望值过时了。

## 5. 内核与 UI 分层：为"双端同源"付出的成本

内核 `guardian/` 有一条硬纪律：**只允许依赖标准库与纯 Python 包，
禁止 import tkinter / fastapi**。

为什么值得为此改变整个目录结构：这类工具最隐蔽的 bug 是**跨端判定漂移** ——
桌面端说"违规"，浏览器体验页说"合规"，同一段文案两个答案。
一旦发生，用户对两个端的信任会同时崩塌。

所以：
- 规则导出成前端 JSON（`scripts/export_web_rules.py`）；
- 用同一批语料对拍两个引擎的结果（`scripts/verify_web_parity.py`）。

代价是要维护导出脚本与对拍脚本，且内核不能图方便直接调用 UI 层的东西。

## 6. 性能：两个把界面毁掉的真 bug

### 6.1 违规列表每行 200px 高

```python
ctk.CTkFrame(row, width=3)   # 给 width，不给 height
```

`CTkFrame` 的 `height` 默认值是 **200**，内部实现是 `canvas + 内部 frame`。
只给 `width` 时 canvas 请求 200px 高度，Tk 取"canvas 请求"与"子控件请求"
的较大值 —— **一条两行文字的违规项占掉 200px 高**。5 条违规浪费 800px，
界面看起来像"没数据"。

同一类问题在仪表盘的条形图里**当天又出现一次**（`CTkFrame(row, width=170)`），
说明它不是一个可以靠"小心一点"避免的错误，而是**组件默认值陷阱**。

于是写了 `tests/test_ui_conventions.py`：静态扫描所有
"只写 `width` 不写 `height` 的 `ctk.CTkFrame`"，并在测试里同时断言
"CTkFrame 默认高度仍然是 200"—— 将来 customtkinter 若改了默认值，
守卫会先失败提醒我们，而不是静默失效。

（守卫本身第一版就误报了：正则 `width=` 把 `border_width=1` 也匹配上了。
已修正为 `(?<![_A-Za-z])width=`。）

### 6.2 切页时"组件一个个画出来"

```python
# 原实现
self.pages[page_key].pack(fill="both", expand=True)   # ① 先上屏
...
if hasattr(page, "refresh"):
    page.refresh()                                     # ② 再重建内容
```

顺序反了。页面先出现在屏幕上（内容是空的或上一轮的），随后 `refresh()`
开始 destroy 并重建子控件 —— 用户于是亲眼看着组件一个接一个画出来。

改为**先 refresh，后上屏**：重建发生在页面不可见的状态，
`lift()` 之后一次性完整显示。

同时把页面切换从 `pack_forget / pack` 改为 `place` 重叠定位 + `lift()`：
前者会触发 Tk 对整棵控件树重算几何（仪表盘 160 个控件实测约 540ms），
后者只改 z 序。

### 6.3 其他两处

- **历史页**：每次切回都重建 100 条记录（约 600 个控件）要 1.0~1.7 秒，
  而多数时候历史一条没变。用 `(id, 分数, 时间)` 序列做签名，未变化就跳过重建；
  容器改用原生 `tk.Frame` 减少 canvas 数量。
- **主题切换**：主题色写死在控件构造参数里（customtkinter 没有批量改色 API），
  切换必须重建页面。直接在原地看着界面逐块变色闪烁，所以加了一层提示遮罩，
  延后一帧再重建 —— 把 1.2 秒的视觉混乱换成一次有反馈的等待。

## 7. 一个反直觉的结论：功能"能跑"不等于功能"有意义"

三平台对比是产品的核心卖点，但它曾经是这样的：

```
小红书 78 / 抖音 78 / 视频号 78
平台差异分析：💡 此文案在小红书合规分数最低（78分），建议针对性修改后再发布。
```

三个平台分数完全一样，却点名了小红书。原因很简单：`min()` 在并列时返回
字典的第一个 key。

更值得反思的是**为什么三平台会完全同分**：因为真实文案里绝大多数命中
来自跨平台通用规则（广告法 485 条 + 行业包 211 条），平台专属规则
（246 条）只在"加微信 / 私信我 / 加群"这类导流表述上才有差异。

所以修法不只是修 `min()` 的 bug，而是让输出**诚实**：

| 情况 | 输出 |
|---|---|
| 三平台同分 | "三平台判定一致（均为 85 分）：命中的是跨平台通用规则，平台之间没有额外差异。" |
| 有差异 | "分数最低的平台：小红书、抖音（90 分），与最高分（96 分）相差 6 分；小红书独有违规：私信我" |

第二种情况下"平台差异分析"才真正有用 —— 它告诉你**这条文案在哪里会被卡**。

这个案例的教训：**实现一个功能之后，要问"它在真实数据上会输出什么"，
而不是"它有没有跑通"。**

## 8. 本地优先，以及 AI 的职责边界

### 8.1 本地优先

内容合规场景下，"文案不出本机"是硬需求 —— 客户发给运营的草稿、
未发布的营销方案，都不应该上传到第三方服务器换取检测结果。

因此：检测全部在本地完成；AI 改写走本地 Ollama（可选）；
历史记录存本地 SQLite（`guardian/storage.py`，原子写入防损坏）。

代价是本地模型的改写质量受模型规模限制（默认 `qwen2.5:7b`），
但这比"把未发布内容上传出去"更容易接受。

### 8.2 AI 只做改写，不做判定

这是本项目后期做的一次**职责反转**，也是最重要的一个判断。

**原来的做法（错的）**：一个「AI 深度检测」按钮，把整段文案丢给模型，
让它输出 `risk_summary`（风险总结）+ `extra_findings`（规则没覆盖的可疑表述）。

看起来很美好，但它让模型去做了**判定**——而这恰恰是模型最不该干的事：

| 判定的要求 | 模型的现实 |
|---|---|
| 今天判 78 分，明天还是 78 分 | 同一句话问两次可能给两个答案，`temperature=0` 也只减少不消除 |
| 每一分都要能追溯到具体法条 | 会引用不存在的法条；在合规场景里，编造的依据比没有依据更危险 |
| 漏检与误报都要可控 | 两个方向都不可控：没见过的变体漏检，看到"第三"就误报排名宣称 |

**改后的做法**：判定 100% 归规则引擎，模型只负责把已经认定违规的话，改成
一句合规但仍有说服力的商业文案。

为什么改写必须给模型？因为规则库能告诉你"《广告法》禁用『最』字"，也能给出
替换词，但它给不出这句话：

> 原文：保签包过，不过全额退款，成功率 100%
>
> 改写：协助准备申请材料、按流程递交，并对可行路径做前置评估；材料准备与递交进度全程跟进。

这句改写做了三件事，全都需要语言能力：把结果承诺换成过程表述、把虚假数字整个
拿掉（不是替换）、把被削掉的卖点用合规方式补回来（"全程跟进"）。

第三条最关键。很多工具改到这里就变成一句废话（"我们做移民的"）——
**合规不等于把文案改得没有说服力**，这个平衡只有语言模型能做。

### 8.3 光在文档里写"不要让 AI 判定"没有用

模型看不到我们的文档。所以这句话必须进提示词，而且**"不要做什么"要写得比
"要做什么"更详细**——模型越界的成本远高于它少做一点。

`guardian/llm/prompts.py` 里的约束（两端共用同一份，桌面端与 Web 端行为一致）：

```
## 你的唯一任务
把下面这段文案**改写**到合规。**不要做合规判定**——违规点已由规则引擎
精确找出并列在下方，你只需要按清单逐处改写。

## 为什么判定不交给你
规则引擎的判定确定、可复现、每条都能追溯到法条；模型做判定会漏检、会
凭空发明违规、同一句话问两次给两个答案。所以：
* **不要**新增清单以外的"我觉着也违规"的判断
* **不要**删除清单以外的任何内容
* **不要**在输出里讨论这段文案合不合规，只给改写结果
```

还有一条容易被忽略的：明确允许模型说"我改不了"。

```
## 拿不准的时候
…把它如实写进 unresolved，说明**为什么改不了**和**需要补充什么信息**。
**不要硬凑一个假方案**。
```

因为模型的默认行为是讨好——你让它改写，它一定会给你一个版本，哪怕是编的。
一个诚实的"这句需要人工确认"，比一个编出来的合规说法有用得多。

这些约束是可验证的：`tests/test_rewrite.py::TestPromptBoundary` 检查提示词里
这几句话还在不在，删掉任何一句测试就红。

### 8.4 "没有 AI 也是完整产品"是底线

三层降级，每层都是可用的产品：

| 情况 | 用户得到什么 |
|---|---|
| 没配任何模型（默认） | 完整检测：命中清单 + 分级 + 合规分 + 高亮预览 + 导出报告，一个功能都不少 |
| 想用 AI，不想配 key | 「复制改写指令」：把命中清单 + 改写约束打包成文本，粘到任意 AI 即可 |
| 配了 Ollama / 云端 API | 检测完点「AI 改写」，直接出改写结果 + 逐处改动对照 |

中间那层（内部叫 BYO-AI）是最划算的设计：用户不用装几个 GB 的模型、文案不经过
任何服务器、用什么模型自己决定，而且还让 Web 体验页可以**纯静态部署**——
没有后端，就没有运维成本，也没有数据泄露面。

底线有测试钉着：

```python
def test_detection_unaffected_by_ai_failure(self):
    """AI 挂掉后，规则检测的分数与命中必须一模一样。"""
```

### 8.5 一个副作用：AI 可以随时挂

因为 AI 在规则引擎的**下游**（输入是已定好的结论，产出不回流影响判定），
调用失败就不算"产品故障"，而是"换条路"——弹窗问用户要不要走复制指令。

这是分层的红利：**依赖是单向的，所以故障也是单向的。**

## 9. 如果重来

- **评测语料应该在第一版就建**。项目早期靠"手感"判断误报，导致走到
  "27 句正常文案里 20 句误报"才发现。先有度量，再有优化。
- **UI 层的组件默认值应该在架构文档里单独列一节**。`CTkFrame` 的
  200px 默认高度用一天时间骗了两次。
- **词库治理从第一天就该脚本化**，而不是等积累了 6 条死规则再回头清理。
- **`min()` / `max()` 在多值并列时的行为**，应该作为 code review 的固定检查项 ——
  这类"看起来对、结果错"的 bug 最难被发现，因为它不报错。

## 附：可复用的工程经验

1. **不要用有限枚举对抗无限变体** —— 找出句式的"骨架"，用模式覆盖整类。
2. **放宽一条规则时，必须同时补一条精确规则兜住边界**，否则是单边妥协。
3. **指标要能被回归**。把"好不好用"变成 `pytest` 断言，才不会被后续改动
   悄悄弄坏。
4. **组件默认值是隐性契约**。把"默认值是多少"写成测试，比写在注释里可靠。
5. **异常在 Tk 回调里抛会静默吞掉**。`_on_detection_done` 里一个
   `NameError` 让"历史不入库""高亮预览永久禁用"两个功能死掉很久而无人察觉 ——
   现在用 `root.report_callback_exception` 挂钩子做验证。
6. **`except Exception as e: lambda: f(e)` 是陷阱**。`e` 在 except 块结束时
   被隐式 `del`，闭包真正执行时名字已不存在。先把值绑定到局部变量。
