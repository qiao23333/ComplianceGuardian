# 合规卫士 v3.0 产品评审（2026-09-14）

> 评审方式：全部结论基于**实际运行与量化数据**，不是读代码的印象。
> 桌面端在真实 mainloop 下启动、逐页截图走查；功能点逐个调用验证；
> 误报/漏检用 61 条评测语料跑指标。

---

## 一、界面设计与视觉：美观吗？

**结论：设计系统是合格的，但两个"看起来像没数据"的 bug 严重拖累了观感。现在已修。**

### 原本合格的部分

- 有真正的设计系统，不是随手写颜色：`apps/desktop/ui/theme.py` 里统一了
  间距（`SPACING`）、圆角（`CORNER_RADIUS`）、字体阶梯（`h1/h2/h3/caption/micro`）、
  语义色（primary/danger/warning/success），深浅色双主题都能跑。
- 自研了三个组件：`GradientCard`（带顶部渐变色条的统计卡）、
  `ProgressRing`（合规分数环）、`BarChart`（词库占比条）。视觉上有记忆点。
- 检测结果页的信息结构是对的：分数环 + 风险等级 → 违规详情（每条带序号、
  分类、来源、改写建议）→ 底部四个动作（复制修改后文案 / 一键改写 / 导出报告 / 重新检测）。

### 实际拖后腿的问题（已修）

| 问题 | 现象 | 根因 |
|---|---|---|
| **违规列表每行 200px 高** | 一条两行的违规占满 200px，5 条违规浪费 800px 空白，看起来像"只检测到 2 条" | `ctk.CTkFrame(row, width=3)` 只给 width 不给 height，而 CTkFrame 的 height 默认是 **200** |
| **仪表盘信息重复** | 同一份词库数据画了两遍（彩色条形图 + 带明细的列表），十行内容只有五个含义 | 历史遗留"保留兼容"的列表没删 |
| **切页时组件逐个"长出来"** | 你反馈的"从黑变正常" | `show_page()` 先 pack 上屏、后 refresh 重建，重建发生在可见状态 |
| **首页空壳感** | 累计检测 0、发现违规 0，四个统计卡全是大号 0 | 缺演示数据/首次引导 |
| 产品名夹个人名 | 侧栏"桥的合规卫士" | 作品展示不该把个人名字塞进 logo，已统一为"合规卫士" |

修复后：违规列表恢复正常信息密度（一屏 4+ 条），仪表盘控件 214 → 160，
切页耗时从"540ms 且可见闪烁"变成"166ms 且一次性完整"。

### 仍然建议改的（按 ROI 排序）

1. **右侧结果区太窄**。当前左:右 = 3:2，结果区被分数环吃掉一大块宽度，
   长建议文本频繁换行。建议改 1:1，或分数环缩到 100px 并改为横排
   （分数环在左、风险等级在右）。
2. **结果区缺少上下文标注**。用户切换平台/账号类型后再看结果，
   不知道这份结果属于哪个平台。应在结果头部加一行
   `小红书 · 蓝V认证 · 08:05 检测` 的元信息。
3. **空态没有引导**。批量检测页是一张巨大的空白卡片。至少要有
   "选择文件夹 → 开始扫描"的分步引导，或"用示例数据试试"。
4. **emoji 当图标不专业**。侧栏用 📊🔍📁 在 Windows 上渲染成彩色 emoji，
   在 macOS/Linux 上是另一套字形。作品级产品建议换成矢量图标
   （或至少统一为单色符号字）。
5. **建议文案质量不齐**。同为高危项，"保证下签"给的是
   "改为'协助递交申请'"（可直接用），"成功率100%"给的是"删除"（无用）。
   建议给每条规则的 `suggestion` 做一次质量普查，缺"替代说法"的补齐。
6. **仪表盘的"999 条规则"是虚荣指标**。用户不关心规则条数，
   关心"能不能查出我这篇文案的问题"。建议把这张卡换成
   "近 7 天检出高危 N 条 / 已修改率"之类与用户价值直接相关的指标。

**结论：能跑，但曾经有两个功能是"死"的 —— 而且界面上完全看不出来。**

### 验证过的能力（全部实测通过）

| 能力 | 验证结果 |
|---|---|
| 单平台检测 | ✅ "保证下签 + 成功率100%" 命中 2 条，分数/等级正确 |
| 三平台对比 | ✅ 修复后能给出真实差异（见下） |
| 蓝V / 非蓝V 差异 | ✅ 57 条蓝V专属限制生效 |
| 批量扫描 | ✅ 3 个文件扫描 + 风险分布汇总 + Top 命中词 |
| CSV 导出 | ✅ 文件生成 |
| Excel 导出 | ⚠️ 原先必然失败（openpyxl 没进依赖清单），已补 |
| HTML / PNG / PDF 报告 | ✅ 三种格式均生成成功 |
| 历史记录 | ✅ 修复后正常入库（SQLite） |
| 高亮预览 | ✅ 修复后按钮可用、标签高亮正常 |
| 词库管理 | ✅ 482 条规则表格 + 增删改 + 备份恢复 |
| 变体抗规避 | ✅ 繁体/拼音/空格干扰还原 |
| 测试套件 | ✅ 233 个用例全通过 |

### 三个 P0 真 bug（已修）

**1. 检测完成后，历史不入库 + 高亮预览永久禁用**

`_on_detection_done()` 最后一行引用了不存在的局部变量 `text` 和 `plat_key`：

```python
self._auto_save_history(result, text, plat_key)   # NameError
```

后果链条很隐蔽：
- 异常抛在 Tk 的 `after` 回调里 → **界面上没有任何提示**；
- 抛出点在 `toggle_btn.configure(state="normal")` 之后? 不 —— 在**之前**，
  所以"高亮预览"按钮永远停在 disabled；
- 历史写入被跳过 → 历史页永远是空的、仪表盘"累计检测"永远是 0。

一个变量名，废掉两个功能，而且用户完全看不出来。**这也是你说"界面很空"的一部分原因。**

**2. LLM 错误回调失效**

```python
except Exception as e:
    self.after(0, lambda: self._on_llm_error(str(e)))   # e 已被隐式 del
```

Python 会在 `except` 块结束时隐式 `del e`，lambda 稍后执行时名字已不存在。

**3. 跨平台对比给出"假结论"**

```
小红书 78 / 抖音 78 / 视频号 78
💡 此文案在小红书合规分数最低（78分），建议针对性修改后再发布。
```

三个平台分数完全一样，却点名小红书 —— 因为 `min()` 在并列时返回字典的第一个 key。

这个问题值得单独说，因为它暴露的是**产品层面**的疏漏而不只是代码 bug：
真实文案里绝大多数命中来自跨平台通用规则（广告法 485 + 行业包 211），
平台专属规则（246 条）只在"加微信/私信我/加群"这类导流表述上才有差异。
所以"三平台同分"是常态，而旧逻辑在常态下必然输出错误结论 ——
**一个在多数情况下给错答案的核心卖点**。

修复后：

| 场景 | 输出 |
|---|---|
| 三平台同分 | "三平台判定一致（均为 85 分）：该文案命中的是跨平台通用规则，平台之间没有额外差异。" |
| 有差异 | "分数最低的平台：小红书、抖音（90 分），与最高分（96 分）相差 6 分；小红书独有违规：私信我" |

## 三、独到性：能讲什么故事？

**结论：有三条真差异化，而且都能落到具体数字和具体设计上。不是"我也有这些功能"式的水话。**

### 差异化一：反误杀设计 —— 最能讲故事的一条

**问题**：通用工具（句易网、零克查词）做的是"违禁词表匹配"。放到移民/留学行业会立刻崩：

```
第一步先准备护照和成绩单，第二步递交EOI        → 报"第一""第二"违规 ❌
第一阶段：评估资质，第二阶段准备材料            → 报"第一""第二""第三" ❌
第1步、第2步、第3步我都写在下方清单里了        → 报"第1""第2""第3"违规 ❌
```

实测：**31 条正常业务文案里 11 条被误报，误报率 35.5%**。
而这些句式是移民/留学文案里出现频率最高的（讲流程、讲材料、讲时间线都靠它）。

**我的做法**：不做"加词/删词"的拉锯，而是把判定拆成两层 ——
**规则层负责命中，语境层负责否决**。

```
豁免语法模式：第[序数](?:个)?(步|阶段|章|节|篇|条|次|天|年|月|周|期|轮|批|版|位…)
              首(个|次)(工作日|自然月|月|季度|阶段|环节|版本|批次)
判定规则：    命中区间被豁免区间完全覆盖时才算豁免
```

**效果（可复现）**：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 误报率 | 35.5% | **0%** |
| 漏检率 | 26.7% | **0%** |

**并且关键的是没有矫枉过正** —— 真极限词全部照报：

```
行业第一的移民机构    → ✅ 报出（"行业第一"是独立词条）
销量第一的咨询服务    → ✅ 报出
我们是首家获批的机构  → ✅ 报出
全网最低价的移民服务  → ✅ 报出（并已提级为高危）
我排在第1位等待补料   → ✅ 不报（位次语义）
```

**讲故事的落点**：这不是"我加了几条词"，而是
"我把一个词表匹配工具，做成了带语境判断的工具，并用可量化的指标证明它可用"。

### 差异化二：三平台 × 双账号的二维矩阵

| 维度 | 具体内容 |
|---|---|
| 平台维度 | 小红书 123 条 / 抖音 63 条 / 视频号 60 条平台专属规则，实测有差异 |
| 账号维度 | 蓝V企业号 57 条专属限制，与个人号标准不同 |

实测差异示例（同一文案）：小红书 90 / 抖音 90 / 视频号 96，
差异来源是"私信我"在小红书独有违规 —— 这是**能直接指导修改**的信息。

### 差异化三：行业词库包的可插拔架构

新增一个行业不需要改一行内核代码：

```
rules/industry_packs/<行业>/
├── pack.json    # id / 名称 / 版本 / 描述 / 分类清单
└── rules.json   # [{keyword, category, severity, suggestion, note}, ...]
```

这解决的是**通用工具的商业模式盲区**：通用工具不可能为每个垂直行业维护红线词库
（市场太小、维护成本高），而行业从业者自己知道红线在哪。
内置移民 178 条 + 留学 33 条；其他行业可以自己加。

### 还有一条"工程差异化"值得提

**内核与 UI 严格分层 + 双端对拍**。`guardian/` 禁止 import tkinter/fastapi，
规则导出给浏览器端，再用同一批语料对拍 Python 与 JS 两个引擎的结果。
这防的是"桌面端说违规、网页端说合规"这类最伤信任的 bug。

## 四、有没有展示制作者的思考？

**结论：有，而且密度不低 —— 但之前全部藏在代码里，对外几乎不可见。现在整理成 `docs/DESIGN.md`。**

代码里能看到的思考痕迹：

1. **反误杀守卫的三道防线**：语境排除 → 短词降级 → 改写安全网。
   其中"禁止对单字词自动改写"是因为发现过一个事故级 bug：
   `"最近很多人问我"` 会被自动改写成 `"近很多人问我"`（直接删掉"最"字）。
2. **"放宽必须成对"的原则**。豁免"第X位"的同时补了
   `(位列|排名|位居|荣登)…第X位` 正则 —— 单边放宽会变漏检。
   这条原则在 `第X位` vs `第X名` 的判断上体现得最清楚（量词表刻意不收"名"，
   因为广告语境里的"第3名"基本就是排名宣称）。
3. **原子写入配置**：tempfile + os.replace，防止崩溃损坏配置。
4. **AC 自动机 vs 纯 Python 双实现**：装不上 C 扩展时自动降级而不是报错。
5. **本地优先的取舍**：语义增强只走本地 Ollama，代价是准确率受限于 7B 模型，
   换来的是"未发布的营销方案不必上传"。

**但之前缺的是"对外表达"**：

- README 停留在 v2.3，写的是已经不存在的 `core/ ui/` 目录结构，
  声称"140 条移民规则"（实际 178）、"25 个测试"（实际 233）、
  还写了一个根本不存在的 API `detector.list_industry_packs()`。
- CHANGELOG 停在 v2.4，v3.0 的三次重构一条没记。
- 没有任何地方解释**为什么这样设计**。

现在补齐了：README 全面重写并对齐真实数据，CHANGELOG 补全 v3.0.0，
新增 `docs/DESIGN.md` 记录每个关键决策的"为什么"与"放弃了什么"。

## 五、PM 视角：还应该做什么（按优先级）

### P0 — 影响"能不能作为作品展示"

1. **首屏演示数据**。现在打开是四个大号 0。应该内置"载入示例"按钮，
   或首次启动带一份演示历史，让用户在 10 秒内看到产品的完整价值闭环。
2. **结果页加"这条该怎么改"的一键落地**。已有"一键改写"，但改写结果
   目前替代原文，用户容易误操作。建议改为"并排对比 + 逐条采纳/忽略"。
3. **README 加截图/GIF**。作品展示最缺的是"打开就能看到长什么样"。

### P1 — 影响可用性

4. **规则质量的持续治理**。本轮修了 6 条死规则、提级 4 条严重度，
   但 999 条里还有多少条 `suggestion` 是无效的（只写"删除"）？
   建议写个 `scripts/audit_suggestions.py` 普查，输出"无可用替代说法"清单。
5. **历史记录缺少平台标签与批量管理**。列表里看不到这条记录是哪个平台
   检测的，也没有搜索/筛选/批量删除/导出。
6. **"清空历史"没有二次确认**。危险操作直接执行。
7. **词库管理页缺搜索框**。482 条规则靠滚动找，右边还并排放着一个
   大红色"删除选中"按钮 —— 危险操作不该和普通操作同级视觉权重。

### P2 — 影响专业度

8. **导出报告的可信度**。报告里应带"本次检测使用的规则版本号 + 词库条数"，
   否则用户无法判断两份报告为何结论不同。
9. **检测结果缺少位置信息**。现在只有关键词，没有"在第几段/第几句"，
   长文案定位成本高。
10. **深色模式下的对比度需要复查**。浅色模式做过对比度整改（有工具脚本），
    深色模式没有系统检查过。
